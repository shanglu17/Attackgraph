# ASTRA 前端开发规范（Agent 优先）

> 状态：生效中  
> 适用范围：`apps/frontend/**`  
> 目标：让页面按用户任务组织，而不是按接口、数据表或开发顺序堆叠。

## 1. 信息架构

ASTRA 固定使用四个顶层工作区，同一时刻只显示一个：

| 工作区 | 状态值 | 用户任务 | 允许的主要内容 |
| --- | --- | --- | --- |
| 图谱分析 | `analysis` | 查看拓扑、运行 DPS、审查攻击路径 | KPI、安全域列表、拓扑、路径排名 |
| 数据导入 | `imports` | 导入并预览外部资料 | F3532、CXF、FHA 导入流程 |
| 报告中心 | `reports` | 生成、核查、导出成果 | F3532 03、vol3 报告与表格 |
| 变更管理 | `changes` | 编辑并原子提交图谱 | 实体编辑器、变更队列、JSON 预览 |

规则：

- 新功能先回答“用户来这里要完成什么任务”，再选择工作区。
- 顶层工作区不是后端模块导航。只有用户目标明显不同，才允许新增工作区。
- 工作区切换只改变可见内容，不应清空用户已加载的数据或草稿。
- 工作区内超过两个相互独立的子任务时，使用局部 tabs、折叠区或拆分页面，不继续纵向堆叠。

## 2. 页面布局

页面从上到下只包含四层：

1. `header`：产品身份与全局动作；
2. `workspace-nav`：四个工作区入口与全局状态；
3. 可选的工作区摘要，如图谱 KPI；
4. `workspace-content`：当前唯一主要任务。

布局约束：

- 宽屏分析区采用 `280px / minmax(0, 1fr) / 340px` 三栏；中间画布永远获得剩余空间。
- 报告与变更管理采用单列，避免宽表和表单被侧栏压缩。
- `1280px` 以下切为单列；`720px` 以下收紧间距并隐藏导航的辅助说明。
- 页面级容器最大宽度为 `1920px`，在超宽屏居中。
- 页面不得出现横向滚动。宽表格、长 JSON 和列表必须在自身容器中滚动。
- 不使用绝对定位拼主布局；不通过随机 `z-index`、负 margin 或固定像素高度修补结构问题。

## 3. 组件边界与目录

目标结构：

```text
src/
  app/                 # App shell、路由或顶层工作区编排
  components/          # 无业务含义的通用 UI
  features/
    analysis/
    imports/
    reports/
    changes/
  api.ts               # 类型化 API 边界
  types.ts             # 跨 feature 领域类型
  styles.css           # tokens、基础组件、布局工具
```

当前 `App.tsx` 是遗留大文件，采用“只减不增”策略：

- 不要求一次性重写；
- 新增超过约 40 行 JSX、含独立异步流程、或拥有 3 个以上局部 state 的区域，必须提取到 `features/<name>/`；
- 提取时由父层传入数据与回调，feature 不复制一套 GraphData 状态；
- 纯显示组件保持纯函数；副作用放在事件处理器或明确命名的 hook 中；
- 不做无关的大范围改名或格式化，避免与业务改动混杂。

## 4. 状态与数据流

- 后端通信只通过 `api.ts`；组件不散落 `fetch`、URL 和响应解析。
- 服务端实体以 `types.ts` 为单一前端类型来源，不在 feature 内复制接口。
- 页面状态分为：服务端数据、用户草稿、界面选择。三类状态不要混在一个对象里。
- 可由现有数据推导的值使用 `useMemo` 或直接计算，不额外存一份 state。
- 切换 tabs/workspace 不清空草稿；只有明确的 Reset、Commit 成功或加载新版本才重置。
- 异步操作必须覆盖 loading、success、empty、error 四种状态，并防止重复提交。

## 5. 视觉与样式

优先复用以下基础类：

- 容器：`.panel`、`.preview-card`、`.scroll-panel`
- 操作：`.button`、`.button.primary`、`.toolbar`
- 表单：`.field-stack`、`.field-label`、`.input-field`
- 状态：`.status`、`.pill`、`.tag`
- 导航：`.workspace-nav`、`.workspace-tab`、`.mode-toggle`

规则：

- 组件用语义 class，具体视觉集中在 `styles.css`；第三方库必要配置除外，不新增大段 inline style。
- 间距遵循现有 4px 基准：常用 `8 / 12 / 16 / 24px`，不引入随意数值。
- 一屏只突出一个主要动作。破坏性动作不得使用 primary 样式。
- 标题层级按 `h1` 产品、`h2` 工作区、`h3` 区块、`h4` 子区块，不用字号模拟标题。
- 空状态说明下一步行动；错误状态说明发生了什么以及用户能做什么。
- 表格表头保持清晰，单元格允许换行；输入框不得被通用 `flex-basis` 撑坏表格。

## 6. 可访问性与文案

- 可点击元素使用 `button`、`a`、`input`，不使用只有 `onClick` 的 `div`；遗留代码被触及时应修正。
- tabs 必须有正确 role 与 `aria-selected`；纯图标按钮必须有可访问名称。
- 键盘焦点必须可见，禁用状态不能只靠颜色区分。
- 同一工作流优先使用同一种语言；标准缩写（DPS、F3532、DO-326A）可保留英文。
- 中文源文件使用 UTF-8，发现乱码应在本次触及范围内修复。

## 7. Agent 工作流程

### 修改前

1. 阅读本规范与 `apps/frontend/AGENTS.md`。
2. 说明功能归属的工作区和主要用户任务。
3. 检查 `git status`，保护用户已有改动。
4. 先运行或确认现有构建基线。

### 实现时

1. 先复用现有组件与样式，再决定是否新增抽象。
2. 不把新业务区域继续塞进 `App.tsx`。
3. 保持加载、空、成功、错误状态完整。
4. 同时考虑宽屏、窄桌面和移动端，不在最后用补丁式 CSS 兜底。

### 完成前

1. 运行 `npm run build -w @attackgraph/frontend`。
2. 检查 `1440×900`：导航、三栏画布、主要动作是否在合理首屏。
3. 检查 `1280×800`：布局是否单列且顺序正确。
4. 检查 `390×844`：无页面横向滚动、按钮可点击、导航可理解。
5. 检查四个工作区切换后状态不丢失，隐藏区域不占空间。
6. 检查控制台无新错误，中文无乱码，表格只在容器内滚动。

## 8. 完成定义

只有同时满足以下条件，前端任务才算完成：

- 用户任务有明确入口，且归属一个工作区；
- 页面只呈现当前主要任务，没有重新形成长页面堆叠；
- 组件边界、API 边界、状态流符合本规范；
- 三档视口检查通过；
- 前端构建通过，无新增 error/warning；
- Agent 的最终说明包含测试结果和仍存在的技术债。

## 9. 当前已知技术债

- `App.tsx` 仍是遗留大文件，后续按 feature 渐进提取，禁止继续增长。
- `xlsx` 与部分业务 bundle 仍有体积提示；后续可按工作区做懒加载和 chunk 拆分。
- 当前没有专门的前端自动化测试脚本；在补齐前，构建与三档视口检查是最低门槛。
