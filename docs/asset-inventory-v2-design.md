# 资产清单 v2 设计文档

## 背景

当前 `docs/资产清单_可导入.xlsx` 存在以下问题：

1. **功能资产过多**：67 条功能资产中大量重复性内容（如 SF.4-SF.23 的状态监控类功能），且代码中功能资产仅做元数据记录，不生成图节点
2. **接口资产过于细碎**：相同 producer→consumer 对因物理接口不同被拆成多行（如 GCU→遥控站 拆成 SI.1 ETH 和 SI.2 RS422）
3. **数据资产与接口资产无关联**：数据资产表和接口资产表在代码中是两条平行线，数据资产无法嵌入数据流链路
4. **缺少域属性定义**：trust_level 等属性只能通过代码中的关键词正则推断，用户不可见不可控

## 设计目标

- **精简**：减少冗余数据，只保留与安全分析和攻击图建模相关的信息
- **建立关联**：数据资产通过"对应接口"列关联到接口资产，通过"所属域"列关联到域属性表
- **域属性可配置**：通过新增的"域属性表"集中定义信任程度和安全域，取代代码硬编码

## 新的 Sheet 结构（4 个 Sheet）

### Sheet 1: 接口资产

| 列 | 说明 | 变化 |
|---|---|---|
| 接口编号 | SI.x | 不变 |
| 产生者 | 数据生产方 | 不变 |
| 用户 | 数据消费方 | 不变 |
| 数据流描述 | 简要说明 | 简化 |
| 物理接口 | ETH/RS422/CAN 等 | 合并行用 `/` 分隔 |
| 逻辑接口 | 协议描述 | 简化 |
| 网络域 | 网络域名称 | 可选，简化 |
| 区域 | 物理区域 | 可选，简化 |
| 目的 | 运营/维护 | 不变 |

**合并策略**：相同 producer→consumer 对合并为一行，物理接口用 `/` 分隔。43 行 → 约 25 行。

### Sheet 2: 数据资产

对齐 ZG-ONE 风险评估报告的数据资产表结构，新增"数据流类型"列，采用六分类法：

| 列 | 说明 | 变化 |
|---|---|---|
| 编号 | DA.x / SD.x | 不变 |
| 数据名称 | 数据资产名称 | 不变 |
| 数据类型 | 外场可加载软件/配置文件等 | 不变 |
| **数据流类型** | CMD/CONFIG/STATE/DATA/LOAD/ALERT | **新增**，对齐 ZG-ONE 分类 |
| **对应接口** | 关联到接口编号 SI.x | **新增**，一对多用逗号分隔 |
| **所属域** | 关联到域编号 D.x | **新增** |
| 说明 | 安全相关说明 | 简化 |

数据流类型六分类（对齐 ZG-ONE 风险评估报告）：
- **CMD**：控制指令（起飞、降落、转速等）
- **CONFIG**：配置数据（电子围栏、航线、参数配置）
- **STATE**：状态数据（飞行状态、导航数据、电池状态）
- **DATA**：通用数据（音视频、日志、诊断数据）
- **LOAD**：可加载软件/固件
- **ALERT**：告警信息

### Sheet 3: 域属性表

| 列 | 说明 |
|---|---|
| 域编号 | D.x |
| 域名称 | 如"地面链路域" |
| 信任程度 | Trusted / Semi-Trusted / Untrusted |
| 安全域 | Internal / External / DMZ / Shared |
| 描述 | 可选 |

### Sheet 4: 功能资产

精简保留与安全分析直接相关的功能资产，去掉大量重复性监控类功能。

## 数据流链路生成逻辑

当前（v1）：
```
接口行: producer → IF → consumer    （生成 DataFlow 边）
数据行: data_asset → owner（正则推断）  （平行，无关联）
```

改造后（v2）：
```
1. 数据资产 DA.x 填写"对应接口"= SI.y
2. SI.y 有 producer=P, consumer=C
3. 生成两条 DataFlow 边:
   P(asset) ──DataFlow──→ DA.x(data)
   DA.x(data) ──DataFlow──→ C(asset)
```

同时，数据资产的"所属域"字段关联到域属性表，可以获取 trust_level 和 security_domain 用于边的属性计算。
